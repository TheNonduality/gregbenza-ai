## Before

Until June 4, 2026 the app could answer questions and nothing else.
[Version one](/projects/first-app/) was a single HTML file with the sales
rules embedded in it, and by the start of June it had [a backend holding the
credentials](/projects/one-worker-backend/) and live figures in place of a
weekly export.

What it had no way to do was store anything. Nothing typed into it survived
the session: no record of a visit, no list of outstanding work, and no
shared state between two people using it at once.

## What shipped on June 4

Accounts, tasks and a diary of interactions, held in the same database
behind the same Worker the rest of the backend already used. Per-person
email and password sign-in replaced a shared passcode. A few hundred shops
were loaded, each with a named owner.

It was built for two users. The whole sales team was using it the day it
appeared, without a training session, and interactions logged by people who
had not been asked to try it appeared the same afternoon.

## The account record

The unit of the system is the shop.

Each account carries its owner, its commercial summary, and a diary: every
visit, call, text and email logged against it by any member of the team,
newest first, attributed to whoever logged it. The commercial figures were
already available from the ERP. The diary is the part that did not exist
anywhere before this release — the shelf talkers that were not put up, the
delivery a buyer asked to move to Thursday, the conversation a case split
was agreed in.

Asking about a shop returns that record assembled: the snapshot, the
figures, and the history. The diary returned includes entries written by
colleagues covering the account, which is the difference between a team's
record and one person's notes.

## Role-scoped visibility

The same screen returns different records depending on who is signed in. A
rep receives their own accounts, history, tasks and figures. An admin
receives everything.

That split is enforced on the server, not in the client. Records outside a
user's scope are never sent to the device, so an out-of-scope shop is not
greyed out or partially returned — it is absent. Every route re-checks the
caller's role rather than relying on an earlier check, and the scoping rules
carry their own automated tests.

## Ownership

Every live shop has exactly one person responsible for it, and the database
rejects a write that would leave a live shop without one, regardless of
which code path issued it. The reasoning behind putting that rule in the
data store rather than in application code is in [the backend
post](/projects/one-worker-backend/).

Ownership is what most other behaviour reads from: who can see a shop, whose
figures its revenue counts toward, and whose list work against it lands on.
That makes a territory change a change to one field with wide effects.

## Reassignment in natural language

An admin moves shops between reps by typing an instruction into the chat
box — the same box a rep uses to ask about their month. There is no form, no
admin console and no deploy involved, and the change takes effect
immediately.

Team administration works the same way: adding a person, changing what
someone is permitted to do, or enabling an integration for an individual are
all typed instructions. The app has no settings screen.

Writes are two-step. Nothing is written on the first pass: the app reads
back exactly what it is about to change — which shops, from which person, to
which — and waits. A one-word confirmation commits it. That step exists
because a typed instruction is easy to get wrong, and a read-back converts a
mistake into a question rather than a write.

## Retention

Deletes are soft. A deleted row is marked and retained rather than removed,
because the business needs to reconstruct what an account looked like at an
earlier date. A history that can be edited down after the fact is not a
usable record.

## Go-live defect

The CRM was deployed the day it was written. An error-handling mistake meant
that failures were reported as an anonymous platform error code rather than
the underlying cause, which made anything that went wrong in the field
difficult to diagnose. The same code had behaved correctly in local
development. It is a failure mode worth watching for in AI-written code,
because the code reads as though it works.

## Effect

Before this release the app was a tool with one user at a time. After it,
it was shared infrastructure: a deploy that broke something broke it for the
whole team, and the team's records lived inside it.
