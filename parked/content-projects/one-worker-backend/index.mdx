## The constraint

The app runs on the sales team's phones as a web app. It needs three sets of
credentials: the Claude API for the chat, the ERP's API for orders and
inventory, and a database for the CRM.

A phone client cannot hold any of them. The app is a web page, so anyone
with the app has its source. The rule set at the start was that the client
holds no secrets at all — not encrypted, not obfuscated, none.

That requires a server to hold the credentials and make the calls. The
implementation is a single Cloudflare Worker: a JavaScript program running
at Cloudflare's edge. Every credential is stored there as a platform secret
and injected server-side. The client sends a request, the Worker attaches
the correct credential, and passes it upstream.

The Worker was written and deployed to production on June 3, 2026, the same
day it was started. It has no framework and no build step, and consists of
two plain JavaScript files.

## One doorway, three upstreams

<Media type="image" src="/projects/one-worker-backend/architecture.svg" alt="An architecture diagram: a phone labeled The App with the note 'holds zero secrets', an arrow labeled 'every request' into a blue-bordered box labeled 'One Cloudflare Worker — the only doorway' with a padlock icon, and three arrows fanning out to Claude API, ERP software (read-only), and D1 database — the CRM, SQLite at the edge." caption="The complete server side: one Worker, holding every credential, in front of three upstreams." />

Everything the backend does routes through that Worker:

- **The Claude relay.** The in-app chat runs on Claude and the Worker holds
  the API key. A server relaying a browser's request inherits the browser's
  identity headers and is rejected for it; the relay strips them before
  forwarding. This surfaced on go-live day and worked correctly in local
  development beforehand.
- **The ERP relay.** Orders and inventory come from the ERP's API, with
  those keys also held by the Worker. The relay is read-only by
  construction: it forwards queries and has no write path, so the app cannot
  modify the system of record.
- **The CRM.** Accounts, tasks and interactions are stored in D1,
  Cloudflare's SQLite service, with the Worker serving as its API.

Authentication follows the same routing. Sign-in happens at the Worker,
sessions are signed tokens, and passwords are hashed server-side. Cloudflare
caps the work a password hash may perform in production and the local
simulator does not enforce that cap, so identical code hashed successfully
in development and was rejected in production. That was found on the second
day of the CRM's life.

## Rules enforced by the database

The CRM's data carries constraints. The primary one is that every live shop
must have an owner — a named person responsible for it.

That rule is not a check in application code. It is enforced by the
database, which rejects a write that would store a live shop without an
owner regardless of which code path issued it. The reasoning is that code
paths multiply and each new feature is another opportunity to omit a check,
whereas a database constraint is a single point every write passes through.

Deletion follows the same approach: rows are marked deleted and retained
rather than removed, because the business needs to reconstruct earlier
states.

## Deployment

A Worker deploys globally in about a second from the command line, so fixes
ship as soon as they are verified.

The same backend runs on a laptop — the same Worker code, local SQLite in
place of D1, and dummy credentials in place of the real ones. That provides
a full local copy of the system that has never contained a production
record, which is where changes are tested first.
