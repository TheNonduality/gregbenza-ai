**This has now been run more than once.** The footage below came off a later
flight, two weeks after the one this post is about, and was recovered the
same way — no reference clip needed the second time, because by then the fix
had stopped being a one-off and become a skill.

  src="/projects/pico-repair/second-repair.web.mp4"
  caption="A later flight, recovered by the same skill — the second time it ran."
/>

The file was the right size to hold a real clip. It just wouldn't open — no
thumbnail, no preview, nothing. The standard fix for this exists
(`untrunc`), but the environment doing the repair had no internet and no
root, so it couldn't be installed. That ruled out reaching for the known
tool and left one option: understand the file format well enough to rebuild
it by hand.

The diagnosis came first, and it was exact: the file's raw video data (the
`mdat` atom) was completely intact. What was missing was the `moov` atom —
the index that tells a player where every frame starts. The air unit lost
power before it could write that index, so the footage existed but was
unreadable. Nothing was lost; the map was just gone.

<Media
  type="video"
  src="/projects/pico-repair/recovered.web.mp4"
  caption="The first 22 seconds of the actual recovered footage."
/>

Rebuilding a missing index means knowing exactly where each frame begins and
ends inside the raw stream. A healthy reference clip from the same air unit
made that possible: its layout was studied byte by byte, and a detector was
written to find frame boundaries by walking the stream and telling real
video frames apart from the camera's own metadata packets mixed in between
them. Before that detector ever touched the broken file, it was run against
the *healthy* one — and it reconstructed all 4,477 of its real frames
exactly. Only once it proved itself on file where the right answer was
already known did it get trusted on the file where it wasn't.

Run against the broken clip, it recovered 16,351 frames — about four minutes
thirty-three seconds of footage — and dropped only the final 67 kilobytes:
one partial frame, right at the instant the recording stopped. Every
recovered frame was then decode-checked across the whole clip. Zero errors.

The file wasn't corrupted by some random fault. It was cut off mid-write
when the air unit lost power before it could finish — exactly the failure
mode the diagnosis predicted from the very first look at the file, and
exactly the kind of break that leaves the footage itself perfectly intact.

The full record — the sandbox constraints that ruled out the easy fix, the
segmented re-encode worked around a hard time limit per command, the
false starts along the way — is what the ask-more buttons are for: click one
and your AI reads the complete account.

The fix became a **skill**, not a one-off: the same method now runs on any
similarly broken DJI/Pavo Pico clip, with the camera's codec profile already
baked in, so a healthy reference clip isn't needed a second time. Both files
below are downloadable — the script was re-run against the original broken
file to write this post, and it reproduced the same 16,351 frames, the same
272.79 seconds, byte-for-byte the same result.
