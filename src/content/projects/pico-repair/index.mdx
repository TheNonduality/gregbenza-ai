## The file

The clip was `DJI_20260620174305_0012_D.MP4` — 1.5GB, HEVC (Main 10),
1440×1080, 59.94fps — pulled off a BetaFPV Pavo Pico 2 running a DJI O3 air
unit. It would not open: no thumbnail, no preview, no playback. The file was
full size on disk.

## What was actually wrong

An MP4 has two atoms that matter here. `mdat` holds the video data itself.
`moov` is the index — the table that tells a player where every frame begins.

The camera writes `moov` last, when recording stops. I pulled the battery while
it was still rolling, so the index was never written. `ffprobe` reports that
condition as `moov atom not found`. Inspecting the file directly showed the
`mdat` atom completely intact.

Nothing was lost. The file was unreadable, which is a different problem from
corruption.

## The standard tool wasn't available

There is a known tool for exactly this failure — `untrunc`. The environment
doing the work had no internet and no root, so it could not be installed. That
left one option: understand the file format well enough to rebuild the index by
hand.

## How it got rebuilt

Rebuilding an index means knowing precisely where each frame starts and stops
inside a raw stream that has no markers you are allowed to assume.

So a healthy clip from the same air unit — `DJI_20260619211444_0008_D.MP4`,
shot the day before — was read byte by byte first, to learn the exact layout,
including how to tell real video frames apart from the camera's own metadata
packets sitting between them. A frame-boundary detector was written from that.

The detector was validated on the healthy file before it was run on the broken
one. On a file where the correct answer was already known, it reconstructed all
4,477 frames exactly. Only then was it run against the file where the answer was
unknown.

## What came out

**16,351 frames. 272.79 seconds — four minutes thirty-three seconds.** A decode
check across the entire clip returned zero errors.

The final 67,142 bytes did not survive: a single partial frame, written at the
instant the recording stopped. The DJI telemetry and metadata track was dropped
from the rebuild by choice, to keep the video recovery itself as reliable as
possible.

## Packaging it as a skill

Two weeks later, on July 4, 2026, the method was run again on a clip from a
different flight. By then it had been written up as a skill with the camera's
codec profile already baked in, so the second repair needed no healthy
reference file at all — just the script. That
second output is H.264 8-bit, the skill's universal deliverable, where the first
repair's raw rebuild is HEVC 10-bit.
