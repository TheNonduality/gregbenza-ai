## The stakes are different this time

The [Games wing](/?p=games) is me playing. This wing is my company's
software — a CRM and operations app I built with AI that a real distribution
business runs on every day. Real sales team, real accounts, real money
moving through it.

This first post is about the foundation everything else sits on. It is
smaller than you'd guess.

## A phone app with a secret problem

The App lives on the sales team's phones. It talks to three things that all
demand credentials: the Claude API for its chat brain, our ERP software for
orders and inventory, and a database for the CRM.

A phone is the worst possible place to keep a credential. Anyone with the
app has the app's code — it's a web page. So the design rule, set on day
one, is absolute: **the phone holds zero secrets.** Not encrypted ones, not
obfuscated ones. None.

That rule needs a server — something that holds the keys and does the
talking. What it got was a single Cloudflare Worker: a small JavaScript
program that runs at Cloudflare's edge, close to whoever's calling it. Every
key the company has lives there as a sealed secret, injected server-side.
The app sends requests to the Worker; the Worker stamps them with the right
credential and passes them along. A gatekeeper, not a middleman with
opinions.

The Worker went from first line to live in production on June 3 — one day.
Not because the problem is trivial, but because the shape is so small: no
framework, no build step, a couple of plain JavaScript files. That
smallness is a feature we've defended since. Every piece of machinery you
don't have is a piece that can't fail quietly.

## One doorway, three rooms

<Media type="image" src="/projects/one-worker-backend/architecture.svg" alt="An architecture diagram: a phone labeled The App with the note 'holds zero secrets', an arrow labeled 'every request' into a blue-bordered box labeled 'One Cloudflare Worker — the only doorway' with a padlock icon, and three arrows fanning out to Claude API, ERP software (read-only), and D1 database — the CRM, SQLite at the edge." caption="The whole backend: one Worker in the middle, holding every key." />

Everything the backend does goes through that one Worker, which routes to
three places:

- **The Claude relay.** The in-app chat is powered by Claude, and the
  Worker holds the API key. First lesson of go-live day: a server calling
  the Claude API on a browser's behalf inherits the browser's identity
  headers, and gets refused for it. The fix — teaching the relay to shed
  what the browser wraps it in — was the first of many "works locally,
  fails in production" moments this platform would teach me.
- **The ERP relay.** Orders and inventory come from our ERP's API. The
  Worker holds those keys too, and this relay is **read-only by design** —
  it will pass questions along, never writes. The app can't corrupt the
  system of record even if it tries, because the doorway physically doesn't
  do that.
- **The CRM.** Accounts, tasks, interactions — the half of the app the
  next posts are about. It lives in D1, Cloudflare's SQLite-at-the-edge
  database, and the Worker is its API.

Auth follows the same one-doorway logic. Sign-in happens at the Worker,
sessions are signed tokens, and passwords are hashed server-side — which
produced my favorite go-live bug: the hashing hit a hard cap that exists
only in production. Cloudflare limits how much work a password hash may do,
the local simulator doesn't enforce the limit, and so the exact same code
hashed happily on my machine and refused in the field. Day two of the CRM
was learning that lesson.

## Rules that live in the database

The CRM's data has laws. The one I'm proudest of: **every real, live shop
must have an owner** — a specific person responsible for it. That law isn't
enforced by a code path someone remembered to write. It's enforced by the
database itself, which simply refuses to save a shop with no owner, no
matter which door the write came through.

That distinction — rules living in the database rather than in the code in
front of it — runs through the whole design. Code paths multiply; every new
feature is a new chance to forget the check. A database constraint is one
wall that every write hits. Nothing is ever truly deleted either; rows are
marked gone and kept, because a distribution business is a business of
disputes, and "what did this look like before?" is a question you must
always be able to answer.

## The job that runs while everyone sleeps

Our ERP has an unusual property: **it keeps no history.** Ask it about
inventory and it tells you about now. Yesterday doesn't exist. Trends,
velocity, "are we about to run out?" — all unanswerable from the source.

So every morning, on a schedule, the Worker wakes up with no request to
answer, photographs the entire catalog's stock levels into the database,
and goes back to sleep. Stock over time is reconstructed from the nightly
photographs — and a missed night is missed *forever*, because there's
nothing to backfill from.

That permanence made the job's failure modes the real design problem, and
both of the ones that happened were **silent**:

1. **The job died mid-run**, leaving a half-written day that looked
   complete. The fix is a completion marker written only after a clean
   finish — a day exists when the marker says so, never because data rows
   happen to be present.
2. **The platform simply never fired the schedule.** No error, no log —
   nothing happened, which is the one thing monitoring can't see. That one
   was revived by a redeploy and survives as the system's quietest failure
   mode: every trend answer now carries a staleness note, so a stale photo
   announces itself instead of impersonating a fresh one.

The schedule gets multiple tries each morning, retries skip themselves if
the day is already banked, and if the last try fails the Worker tells the
admin directly. Designing for the failure you can't see coming turned out
to be most of the work.

## Shipping in seconds, rolling back in minutes

A Worker deploys globally in about a second from my terminal, which sets
the tempo for everything: fixes ship the minute they're verified.

The discipline that makes that speed safe was proven the hard way on July
29. A change to how sales numbers are filtered went out, was discovered
wrong in the field, and was **rolled back — verified, live — in about four
minutes**: check out the last good version, rebuild, ship, confirm the live
build stamp. The deploy script verifies the stamp itself, so "did the
rollback take?" is answered by the tooling, not by hope.

And because the whole backend runs identically on a laptop — same Worker,
same database engine, local SQLite standing in for D1, fake keys standing
in for real ones — there's a complete sandbox of the company's entire
system that has never contained a real record: every experiment happens
there first, before it goes anywhere near the field.
